---
title: Validator failover control plane
description: Operator application for observing and safely promoting a warm Sui validator
---

The Tomodachi failover control plane is the operator-facing layer above the
external validator signer. It presents the primary and backup side by side,
evaluates promotion readiness, and performs an immediate fenced handoff without
an on-chain metadata transaction or an epoch-boundary wait.

“Immediate” means one signer lease handoff, normally a few seconds. It does not
mean that two validator processes are briefly allowed to sign. The signer, not
the web application, is the single-active safety authority.

## Components

```text
            +-------------+       same-origin       +-------------+
 operator ->|  dashboard  |------------------------>| control API |
            +-------------+     bearer token        +-------------+
                                                           | server-held mTLS
                                  +------------------------+------------------+
                                  |                        |                  |
                                  v                        v                  v
                         +--------+--------+      +--------+--------+  +------+-------+
                         | primary agent   |      | backup agent    |  | signer status|
                         | sui-node active |      | observer warm   |  | read-only cert|
                         +--------+--------+      +--------+--------+  +------+-------+
                                  |                        |                  |
                                  +------------------------+------------------+
                                                           v
                                                +----------+-----------+
                                                | external signer      |
                                                | one lease generation |
                                                | durable decisions    |
                                                +----------------------+
```

The browser-rendered dashboard calls only the same-origin control API. The
server reads Sui metrics from both nodes, signer status over mutually
authenticated TLS, and supervisor status from a small host agent. Signer and
agent certificates never enter browser storage. The signer's own certificate
allowlist enforces that the control identity can read status and public keys but
cannot acquire a lease or sign. The host agent exposes a narrow allowlist of
operations; it is not a remote shell.

The first deployment binds the control API to loopback and reaches it through
an SSH tunnel. The operator bearer token is stored only in browser
`sessionStorage`; it authenticates an intent to the controller and is not a
signer credential.

## Readiness view

The comparison view must show at least:

- process and supervisor state;
- current epoch and executed checkpoint;
- consensus last commit index and observer subscription progress;
- checkpoint and commit lag relative to the primary and an independent Testnet
  endpoint;
- protocol, worker, and network public-key fingerprints;
- exact observer profile, validator profile, and validator network-key file
  digests enforced by each host agent;
- signer lease holder, generation, and signer-owned expiry;
- voting right and current committee identity;
- signer-owned randomness DKG status and whether shares are ready; and
- time synchronization, disk space, database health, and recent crash loops.

Promotion is disabled when identity fingerprints differ, the backup is outside
configured lag bounds, its database is unhealthy, the signer is unavailable,
or a different promotion operation is already in progress. A missing or
incomplete signer-owned DKG session is a hard readiness failure, not a warning.

## Fenced promotion

Every promotion has an immutable operation ID, expected source lease
generation, source and target host IDs, and a complete audit trail. Its durable
state machine is:

```text
READY -> DRAINING_SOURCE -> WAITING_FOR_LEASE_FENCE
      -> STARTING_TARGET -> VERIFYING_TARGET
      -> STARTING_SOURCE_OBSERVER -> COMPLETE
```

The control API performs these steps:

1. Re-read all readiness inputs and bind them to the promotion operation.
2. Stop the source validator and request a graceful signer lease release.
3. If the source cannot release, wait for the signer-owned lease expiry. Never
   override an unexpired lease from the dashboard.
4. Confirm that the signer reports no active source lease and that the source
   host agent reports the validator stopped.
5. Activate the backup's validator profile and start `sui-node`. The node
   acquires the next signer lease generation before it can sign.
6. Verify the target owns the lease, proposes Mysticeti blocks, advances commit
   and checkpoint metrics, and has no key or committee mismatch.
7. Only after the target is verified, activate the old primary with its
   independent observer profile. Mark the operation complete after that
   observer process is running; it must become warm before a reverse promotion
   is allowed.

Rollback is another promotion in the opposite direction. It first fences the
new primary and waits for its lease release or expiry; it never starts the old
primary as a shortcut.

## Service configuration

Run one `sui-validator-agent` on each validator candidate. Its controller
client certificate allowlist is independent of the signer's lease-holder
allowlist. The service name and all profile paths are fixed configuration, so
the controller cannot supply an arbitrary unit or path:

```yaml
# /etc/sui/validator-agent.yaml on validator-a
listen-address: "0.0.0.0:19001"
authorized-client-certificate-digests:
  - "<control service client certificate BLAKE2b-256 DER digest>"
agent:
  host-id: validator-a
  service-name: sui-node.service
  systemctl-path: /usr/bin/systemctl
  active-config-path: /etc/sui/active-node.yaml
  observer-config-path: /etc/sui/profiles/observer.yaml
  validator-config-path: /etc/sui/profiles/validator.yaml
  validator-network-key-path: /etc/sui/validator-keys/network.key
  state-path: /var/lib/sui-validator-agent/state.bcs
  observer-profile-digest: "<BLAKE2b-256 digest of exact observer.yaml bytes>"
  validator-profile-digest: "<BLAKE2b-256 digest of exact validator.yaml bytes>"
  validator-network-key-digest: "<BLAKE2b-256 digest of exact network.key bytes>"
  protocol-public-key: "<192 lowercase hex characters>"
  worker-public-key: "<64 lowercase hex characters>"
  network-public-key: "<64 lowercase hex characters>"
tls:
  certificate-path: /etc/sui/agent-tls/server.crt
  private-key-path: /etc/sui/agent-tls/server.key
  client-ca-path: /etc/sui/agent-tls/client-ca.crt
```

The control service uses its dedicated status-reader certificate when it
connects to the signer and its controller certificate when it connects to each
agent. It refuses a non-loopback listen address:

```yaml
# /etc/sui/validator-control.yaml
listen-address: "127.0.0.1:19100"
state-path: /var/lib/sui-validator-control/state.bcs
api-bearer-token-path: /etc/sui/validator-control/token
max-checkpoint-lag: 5000
max-commit-lag: 10000
poll-interval-ms: 500
handoff-timeout-ms: 90000
metrics-timeout-ms: 2000
signer:
  endpoint: "https://validator-signer.internal:19000"
  server-name: validator-signer.internal
  ca-certificate-path: /etc/sui/control-tls/signer-ca.crt
  client-certificate-path: /etc/sui/control-tls/status-reader.crt
  client-private-key-path: /etc/sui/control-tls/status-reader.key
  expected-protocol-public-key: "<192 lowercase hex characters>"
  expected-worker-public-key: "<64 lowercase hex characters>"
  request-timeout-ms: 1000
  lease-ttl-ms: 5000
hosts:
  - host-id: validator-a
    expected-holder-id: "<validator-a signer client certificate digest>"
    metrics-url: "http://validator-a.internal:9184/metrics"
    agent:
      endpoint: "https://validator-a.internal:19001"
      server-name: validator-a.internal
      ca-certificate-path: /etc/sui/control-tls/agent-ca.crt
      client-certificate-path: /etc/sui/control-tls/controller.crt
      client-private-key-path: /etc/sui/control-tls/controller.key
      expected-host-id: validator-a
      request-timeout-ms: 2000
  - host-id: validator-b
    expected-holder-id: "<validator-b signer client certificate digest>"
    metrics-url: "http://validator-b.internal:9184/metrics"
    agent:
      endpoint: "https://validator-b.internal:19001"
      server-name: validator-b.internal
      ca-certificate-path: /etc/sui/control-tls/agent-ca.crt
      client-certificate-path: /etc/sui/control-tls/controller.crt
      client-private-key-path: /etc/sui/control-tls/controller.key
      expected-host-id: validator-b
      request-timeout-ms: 2000
```

The token file, controller state directory, and every client private key must
be readable only by the control service account. The bearer token must contain
at least 32 non-whitespace bytes.

The agent verifies all three configured file digests at startup, on every
status read, and immediately before a profile activation. A changed profile or
network key therefore makes readiness fail closed. During preflight, the
controller also reads the signer's public keys with its read-only identity and
requires them to match the protocol and worker fingerprints reported by both
agents.

## Control API sketch

The initial API is deliberately small:

```text
GET  /api/v1/overview
POST /api/v1/promotions
GET  /api/v1/promotions/{operation_id}
```

Creating a promotion requires an immutable operation ID, source and target host
IDs, and the exact expected source lease generation. The dashboard additionally
requires the operator to type the target host and acknowledge the stop/fence
sequence. The server executes the operation as a background job and persists
each safety phase, so an identical request can resume after a process restart.
Cancellation and an append-only operator audit journal are release-gate work;
the current controller never provides a force or fence-bypass operation.

Automatic failover is out of scope for the first release. The first version
provides excellent evidence and one deliberate promotion action. Automation can
be enabled only after repeated fire drills establish safe thresholds for lag,
network partitions, slow shutdown, signer loss, and restart recovery.

## Integration drill

The `fenced_handoff` integration test starts real mutual-TLS signer and agent
servers with separate source, target, status-reader, and controller
certificates. It prepares signer-owned randomness shares, gives the source a
live lease, and deliberately retains that source client while the controller
performs a handoff. The target must acquire a strictly higher generation and
advance validator metrics. A final signing attempt using the source's stale
credential must receive `PermissionDenied` from the signer.

This proves the networked stop/fence/start path and stale-holder rejection. It
is complemented by a real four-validator local Sui swarm test in which one
committee validator has only remote protocol and worker signing authority. That
validator executes checkpoints, crosses an epoch, completes signer-owned DKG,
restarts, acquires a higher lease generation, and resumes progress while its
configured local keys are unrelated decoys.

Together these tests cover the real Sui signing paths and the networked
stop/fence/start orchestration. They do not replace the release-gate drill with
two real `sui-node` processes, Testnet traffic, host/process failures, and a
rehearsed rollback.
